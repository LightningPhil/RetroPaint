# Source review and baseline identification

The catalogue was grounded in README, the actual controls in index.html, dynamically built UI definitions, state/type enumerations, drawing and interaction paths, photo recipes and session rules, project and image codecs, draft storage, enhancement controls, and CAD definitions and worker behavior. Existing browser check definitions were read for risk and workflow context. No application test result was transferred into this catalogue.

Baseline Git HEAD: `c85f751a2e6273da74b94aa76f00ff419fe0186b`. The checkout also contains uncommitted work. [source-snapshot.json](source-snapshot.json) records file hashes and working-tree state; HEAD alone is not this source baseline.

[SOURCE-CONTROL-INVENTORY.csv](SOURCE-CONTROL-INVENTORY.csv) contains 587 literal control/data/label references in the reviewed entry-point files. This is a static navigation aid, not a complete runtime DOM audit: template expansions, generated buttons, canvas hit regions and keyboard-only behavior need the explicit coverage matrix and later real UI testing.

[EXISTING-CHECK-INVENTORY.csv](EXISTING-CHECK-INVENTORY.csv) lists 189 detected named check definitions for navigation. It is not a claim that each definition ran or closes a new case. Dynamic test registration or differently named helper calls may not appear in this static list.

## Intentional limits of this review

The documentation covers the discovered user-facing feature surface and its cross-cutting behavior. It does not certify every internal helper function, every browser, every kernel combination, every possible image, or unimplemented future features. Source hashes let a future tester identify drift. Add a case and retain its new stable ID when a new user-facing function appears, and investigate any runtime control that is not represented in the family matrix.
